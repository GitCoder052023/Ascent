# Security and Privacy Policy

## 1. Scope & Operational Posture

**Ascent** is an open-source experimental research instrument and machine learning pipeline for indoor multi-floor localization and spatial telemetry. Because this project interacts directly with low-level device hardware, wireless radio interfaces (Wi-Fi), and continuous physical motion sensors, maintainers place paramount importance on maintaining both **system security** and **user privacy**.

---

## 2. Privacy Policy & Sensor Telemetry Disclosures

Given the nature of multimodal physical data collection, Ascent handles data streams that can possess significant privacy implications if exposed or shared carelessly.

### 2.1 The Local-First Architecture Guarantee
* **Zero Telemetry Exfiltration:** Ascent contains **no** remote telemetry phone-home endpoints, tracking daemons, advertising SDKs, or cloud-synchronization backends. 
* **Sandboxed Persistence:** All raw sensor readings (accelerometer, gyroscope, barometer) and ambient wireless signatures (SSID, BSSID, RSSI) are written strictly to an isolated, application-sandboxed SQLite database on the physical device.
* **Explicit User Export Only:** Data leaves the host device exclusively when the user manually initiates an export action (such as invoking the native system share sheet to export a CSV artifact).

### 2.2 Sensitivity of Collected Modalities

When capturing or sharing datasets generated by Ascent, researchers and contributors should be conscious of the following privacy characteristics:

| Modality | Ingested Data Points | Potential Privacy & De-Anonymization Risks |
| :--- | :--- | :--- |
| **Ambient RF Topology** | Wi-Fi BSSID (MAC address), SSID (network name), RSSI (dBm), frequency band | **Geographical De-anonymization:** BSSIDs are globally unique hardware identifiers. Public wardriving repositories (e.g., WiGLE, open geolocation databases) allow reverse-lookup of BSSIDs to exact physical building addresses. Sharing unhashed BSSIDs can expose private homes, offices, or sensitive facility locations. |
| **Inertial Kinetics (IMU)** | 3-axis Accelerometer, 3-axis Gyroscope | **Biometric Gait Fingerprinting:** High-frequency inertial time-series can capture unique human gait dynamics, physical cadence, and behavioral motion signatures that may identify individuals. |
| **Micro-Altimetry** | Barometric Atmospheric Pressure | **Vertical & Spatial Profiling:** Continuous pressure time-series expose exact floor changes, elevation profiles, and movement timing within multi-story structures. |
| **Ground-Truth Labels** | Floor numbers, stair traversal markers | **Locational Context:** Labels explicitly document physical behaviors and zone occupancies within a surveyed facility. |
| **Hardware State** | Device model, OS version, screen/lock status | **Device Fingerprinting:** Device configurations can contribute to device-level fingerprinting across disparate datasets. |

### 2.3 Recommended Privacy Practices for Dataset Sharing

If you use Ascent to collect datasets intended for public release, benchmarking, or research publications, we strongly recommend implementing the following privacy sanitization steps prior to distribution:

1. **Hash or Pseudonymize BSSIDs and SSIDs:** Replace raw BSSIDs and network names with salted, one-way cryptographic hashes (e.g., `HMAC-SHA256(bssid, salt)`) to preserve cluster consistency for machine learning without disclosing real-world MAC addresses.
2. **Relative Timestamping:** If absolute time-of-day exposes personal activity routines, normalize chronological fields to relative offsets ($t_0 = 0$) and strip absolute ISO-8601 wall-clock timestamps.
3. **Redact Device Metadata:** Strip or generalize host hardware identifiers (`deviceModel`, `osVersion`) if sharing anonymous corpora.

## 4. Reporting Security Vulnerabilities & Privacy Flaws

If you discover a security vulnerability, credential leakage, unintended network transmission, or a critical privacy issue in Ascent, please report it responsibly.

### How to Report
* **GitHub Private Advisory (Preferred):** Submit a private report via the **Security** tab of this repository by selecting **"Report a vulnerability"**.
* **Direct Maintainer Contact:** Alternatively, contact the repository maintainer directly through the contact details listed on their GitHub profile.

### What to Include in Your Report
To assist in rapid triage and remediation, please include:
1. A clear description of the vulnerability or privacy risk.
2. The specific module, component, or file affected.
3. Step-by-step reproduction instructions or a minimal Proof of Concept (PoC).
4. An assessment of potential real-world impact (e.g., unauthorized data leakage, local privilege escalation).

### Disclosure Timeline
* **Initial Response:** Maintainers aim to acknowledge receipt of security reports within **48–72 hours**.
* **Resolution & Patching:** Maintainers will collaborate with the reporter to investigate the issue, prepare a patch, and coordinate a responsible disclosure release.

Please **do not** file public GitHub issues for undisclosed security vulnerabilities or data leakage bugs until a patch or mitigation has been arranged.
